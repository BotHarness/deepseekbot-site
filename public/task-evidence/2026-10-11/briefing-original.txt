核心观察一｜先分清维护者与安装包
事实：S1-E1 称 DeepSeekBot 由 BotHarness 维护、以 deepseekbot 插件装入 DSH；S1-E2 指出 FeiZhuLulu 的 DS Bot 使用 ds-bot，是另一个独立项目，两者均基于 DSH、均非 DeepSeek 公司官方产品。S2-E1/S2-E3 同样把 DS Bot 描述为 DSH 插件，并声明其为独立社区项目、非官方。S3-E1 说明 DSH 由 DeepSeek AI 开发，处于 developer preview。
推断（依据：上述四条；条件：仅限文档表述）：上游官方身份不能传导给第三方插件；选型应按 owner＋包名＋固定 SHA 三者核对，仅凭 “DeepSeek” 字样容易混淆。

核心观察二｜持续协作机制的设计路线不同
事实：S1-E4 把 Memory 描述为普通 Git 工作树，Group 中消息保留各 Bot 身份、需要时直接 @，授予 Workspace 后可委派独立 Assignments 并各留 Session 与报告；S1-E1 称每个 Bot 保留自己的文件与历史并跨对话/Session/Workspace 延续；S1-E4 另有每条消息/摘要/仅直接提及/静默的收件提醒偏好。S2-E2 描述主 Bot Chief 权限很高、管理其他 Bot 与群聊，群内 admin 默认应答并调用成员，也可直接 @ 某个 Bot。
推断（依据：两源作者自述；条件：未核验实现）：前者把长期协作绑定在文件/Git 与显式授权委派上，后者绑定在以主 Bot 为中心的层级协调上；哪种更省日常研究与跟进成本，资料未给数据。

核心观察三｜成本、数据与版本边界目前只有作者表述
事实：S1-E1 称模型额度由使用者自付、持续后台任务需宿主在线；S1-E2 称远程模型调用时相关上下文仍会发给所选服务商；S1-E5 明确 2026-10-11 当前源码包含 Computer/Browser Bundle，而正式 npm 1.2.0 不含，且源码中新 Bot 仍需显式开启对应 Access。S2-E3 称数据位于 DSH home 的 bot/ 与 sessions/、卸载不删除，Bot 使用用户额度并可读写文件、运行命令。S3-E1 警告会出现破坏性兼容变更。
推断（依据：S1-E5；S2-E3 与 S1-E2 对照）：源码能力不能写成 npm 1.2.0 已交付；“数据留在本机”只是存储位置表述，不能推出远程模型不接收上下文或不存在泄露。
