# SEO AX editorial workflow

Internal standard for bilingual content and distribution. This is not a public blog or a new navigation section.

## 1. Load authority and claim the task

Read the canonical [bot-seo shared-VPS runbook](https://github.com/BotHarness/bot-seo/blob/main/docs/maintainers/shared-vps-seo-ax.md), its keyword-research, seo-report, and openseo-review-web-content skills, then the relevant content brief, video evidence, verification notes, and current GitHub issue/comments/PRs. Use [the product AX adapter](https://github.com/BotHarness/BotHarness/blob/main/docs/agents/seo-ax.md) for access and product evidence. Do not adopt an untracked draft as a competing standard.

Reuse the existing deepseekbot.app server project after live tool discovery and context/report reads. All machines contribute to that shared record; a local localhost OpenSEO instance is not the shared VPS. Private connection values stay machine-local. Assign a coordinator and non-overlapping worker tasks; shared context has one writer and requires read-before-write/readback. Do not overwrite concurrent reports. Follow the canonical explicit write and paid-call approval boundaries.

Completion: one issue has a reader need, claimed owner, evidence scope, selected page/query/locale, explicit market filters, baseline or `unknown`, and a shared-report subject. Norms land before opening the blog-production queue.

## 2. Plan both markets, without duplicate content

The reader journey is installation → first low-risk task → product selection. Reuse the current installation, Telegram, permissions, remote-workspace and comparison guides where they satisfy that intent; create a new page only for a genuine gap. Do not edit unrelated or observing targets.

| Market  | Content and distribution planning                                                                                                                                         |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Chinese | Native Chinese task guidance; consider Chinese developer communities, Bilibili, and local search intent; confirm each platform's current posting rules before publication |
| English | Native English task guidance; consider Reddit, YouTube, developer communities and search intent; confirm community rules and disclose project affiliation                 |

These are candidate channels, not a promise of backlinks, indexing or ranking. Each locale has explicit engine/country/language/device filters and its own measurement; the OpenSEO project's US/English default is not the global strategy. Paired articles need matching facts and strength of claims, not sentence-by-sentence translation.

No paid promotion. Coding-agent subscriptions provide production capacity with human review, not autonomous account operation. One transparent project identity supplies a useful parent article plus differentiated channel adaptations; no fake independent endorsements, copy-paste matrix or keyword-stuffed near-duplicates. Posting itself requires authorization and platform compliance.

## 3. Produce task-level evidence

First planned task slices:

- **Briefing:** synthesize three public sources; retain source links, inputs and outputs; inspect citation accuracy, factual errors and omissions, and record manual corrections. Do not preselect a success result.
- **Coding:** add unit tests to one function in a demonstration repository; record the starting pin, branch, permission scope, prompt, diff, test command/result and manual corrections. Do not infer full repository-delivery capability from a shell demonstration.

Use real high-resolution UI captures with readable text, locale/theme/version and capture date. Keep the original and a sanitized public version; annotate derivatives with attractive frames, focused crops and highlights when useful. Explain annotations without changing product controls/results. Redact secrets/private chats; do not invent screenshots, upscale low-resolution captures as proof, or confuse a diagram with execution evidence. Use the existing PR asset flow for changed UI; docs-only norms do not require staged fake product screenshots.

For comparison work, preserve the established boundaries:

- This is source-based comparison unless a task was actually run by the site. Nine YouTube descriptions/chapters are not complete subtitle/frame verification. Author-reported results remain author reports; retain Cue paid-partnership and Muse referral disclosures.
- DeepSeekBot's established baseline is the checked npm 1.2.0 release, without optional Computer/Browser components. Self-hosting requires configuration, host availability, updates and model/API costs; do not imply absolute privacy or complete data sovereignty.
- Distinguish Grok's shared cloud computer from separately authorized local execution; Cue does not inherit all Manus functionality; Dots, ChatGPT Work and Codex are distinct experiences.
- Unchecked capability = unverified, not unsupported. No invented speed, success rate, efficiency, ranking, best-product conclusion, keyword volume or KD. Recheck official sources and record dates before updating version, plan, price or region claims.
- For same-name projects, use their exact owner/repository/package identity and timestamped evidence. Do not claim an independent domain automatically outranks GitHub or claim media coverage/search demand without evidence.

Completion: an evidence ledger distinguishes official documentation, author reports, site execution and remaining questions; both locales respect the same limits.

## 4. Edit and review through the existing blog pipeline

Answer “which should I choose and why?” early with conditional recommendations. Prefer concise tradeoff tables and concrete task steps; remove repetitive editorial-process warnings but retain limitations that affect selection. Be explicit about DeepSeekBot maintenance cost, without forcing it to win.

Keep JSON frontmatter, slug, publication date, language paths and the comparison keyword `personal AI agents comparison` for the existing article. No body H1 or generated HTML edits. If changing a title/share card, follow README's cover-generation pipeline and inspect both languages. No new category/navigation is implied.

Human review checks reader utility, source strength, native phrasing, paired factual promises, image readability and platform suitability. Run `pnpm verify` before delivery; report actual tests/checks and exact head separately from CI, human QA, merge and production publication.

## 5. Persist, track, decide

Save the task report/research-log entry in shared OpenSEO through the canonical coordination procedure and confirm by readback. Public GitHub records only sanitized evidence and decision references, never private project IDs or dashboard URLs. Do not replace an existing report without ownership/authorization or invent server persistence after a local write.

Each ranking loop targets one keyword/page, with separate locale filters. A paired release can share a PR; its ranking decisions cannot collapse Chinese and English into one average. Capture deployment time and comparable baseline/after windows. Respect the existing seven-day observation/cooldown: zero edits to the observed target until review. Keep the issue's current achieved/active/revert criteria (including the greater-than-three-position drop rule); insufficient data is inconclusive, not achieved.

Business outcome is installation plus a completed low-risk task. Installation-link clicks measure intent only. Until real instrumentation establishes completion, activation is `unknown`; planned GA4 or scheduled Bot tracking is not shipped proof. GSC impressions, clicks and average position support the existing ranking judgement, not a claim of business conversion.

Completion: a human-reviewed issue records the measured result, limitations and authorized next action. Do not merge, deploy, schedule, or operate an external account merely because the research finished.
