### Git/source traps for the author

- **Do not lift the old accepted-commit model from ADR-0047.** [ADR-0047 at the release pin](https://github.com/BotHarness/DeepSeekBot/blob/271e056aecd7f10bd71128a78d2ac9acbea898ea/docs/adr/0047-memory-is-an-optional-git-backed-service.md) contains earlier updates; ADR-0068 expressly supersedes its acceptance gate, Markdown-only validation and linear-history requirements. The normal working tree, not an auxiliary audit ledger, is the authority for current files.
- **Do not flatten Soul and memory into “all remembered text is always in context.”** Standing identity/index and tool-read detail files are distinct layers. Session history and persistent files are not interchangeable; recording a useful note requires actual file contents to exist.
- **Do not promise private-local processing from local storage alone.** A configured remote model can receive prompt/context contents. Self-hosting adds setup, maintenance, storage/backups and host uptime responsibilities; model/API costs depend on the selected provider. No cost benchmark or privacy guarantee was verified here.

## Proposed informational workflow — hypothetical, not execution evidence

1. Use a deliberately non-sensitive, disposable project copy containing public README/design notes. Ask a reader Bot to extract a small set of findings with relative file paths and unresolved questions; explicitly prohibit project edits, execution, network calls and external actions. Before granting access, inspect the actual file/tool authority. Do not call the default Assignment mode a read-only sandbox.
2. Review the findings manually. Only after an explicit decision to persist them, keep topic notes in a separate Bot Memory file and a short pointer in `MEMORY.md`; reserve `SOUL.md` for stable working principles. Writing Memory is itself a write even when the source-project task is read-only: separate those two scopes clearly.
3. Inspect changed Memory files and Git status/diffs; review or explicitly commit intentional changes. Do not promise a clean history or auto-commit after every turn. Validate whether the next Session actually finds the note; persistent storage alone is not successful recall.
4. A second, differently named reviewer Bot can discuss the note in a Group. Label its identity/role separately and do not imply it automatically shares the first Bot's detailed memory. If independent project execution is needed, explain Assignment delegation as a separate, authorized step, not an automatic consequence of Group conversation.
5. Mention compatible DSH extensions only where they fill a specific need. This reading-notes example requires no browser/computer automation or messaging-account connection; do not add plugin/provider capabilities as implicit prerequisites or pretend an integration was tested.

These are authoring suggestions inferred from the sources, **not instructions already carried out or a successful product demo**. Example file names, Bot roles and notes must remain clearly fictional; no real project/profile/user values belong in the article.
