## 发稿顺序与用途

| 阶段           | 先准备/审阅的材料                               | 解决什么问题                                                   | 决定进入下一阶段的证据                                       |
| -------------- | ----------------------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------ |
| 1，开发者先行  | 掘金/技术派候选稿；英文 Hashnode 候选稿         | 建立清楚的项目身份与机制，得到安装、记忆、授权、交付的具体反馈 | 有真实发布链接及可归因反馈；不是以未验证流量或 stars 为门槛  |
| 2，媒体与 V2EX | 量子位/创事记 pitch 与事实包；V2EX 适当节点自荐 | 让编辑和技术社区了解故事与取舍                                 | 真人作者、规则与素材授权完成；实测型报道所需任务证据实际存在 |
| 3，知乎/公众号 | 问题式选型回答；知识工作者长文                  | 回答怎么开始、怎样验收、为什么需要维护                         | 匹配真实问题与作者身份；AI 标识、原创及推广规则核对          |

渠道顺序是用户确认的生产/发布优先级，不是假设的触达规模。可以并行准备后层稿件，实际投递由人类逐层决定。V2EX 是技术社区；技术派当前核验为 paicoding 编程社区，若用户指的是另一平台，应先确认准确网址，不能臆造媒体邮箱。

## 内容与发布的界限

所有外部正文有完整阅读价值、项目关系与事实来源；没有假独立测评、虚构用户经历、待运行任务的成功结论或关键词堆砌。平台会限制链接/推广，备稿完成不等于可立即发布。

DEV 当前 AI 辅助推广规则不适合此轮项目稿，后备而非默认发布。掘金/知乎部分规则与当前发布表单待真人补核；公众号 AI 标识与原创声明单独判断。Hashnode 独立改写稿不能假借另一个页面 canonical；同文转载才使用对应原文 canonical。

官网 #76/#77 的任务结果还没补齐。运行它们需实际 DeepSeekBot/DSH 环境、公开 fixture、明确模型/费用授权和真实截图/日志；本轮没有用文案替代执行证据。此前 9 条视频也不是完整字幕/音画审计，这里没有扩张成新实测。

## 交给 Gemini 的编辑要求

请优先编辑准备稿中的正文，保留与实际发布人的关系披露，按渠道读者独立组织叙述。事实以 [平台证据](platform-evidence.md)、[采样记录](sampling-findings.md)和已上线资料为准。版本从正式 npm 1.2.0 与源码选项分开；`ds-bot` 是另一个维护者的产品；不要把“未核验”改成“不支持”。

允许优化标题、段落、案例解释和语言流畅度；新的产品、价格、功能、排名、运行结果或媒体关系需先补证据。保留所有待补的真实任务字段，不能填入想象结果。官网最终文章走已有双语流水线及人工审核，外部投稿/发帖另行授权。
