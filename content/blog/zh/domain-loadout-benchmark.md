月底算提成的那天，表格几乎从来不会完全照着制度走。刚拉出账单，就有人月中离职需要交接，有一单联合销售要按 50/50 拆给两位同事，有一笔部分退款得扣回，还有几笔账单按规则应该算进下个月。排班考勤和竞品调价也一样——临时换班、按部门执行不同的节假日政策、预订平台（OTA）突然挂出含早价，这些偏离“标准流程”的例外，在一线实际工作里往往吃掉 **80% 以上**的处理时间。

企业想把这类后台工作交给 AI 时，通常会走向两条截然不同的路：

1. **决策式模型（例如 TypeSafe 的 JEV）**：把业务预先归类成一组已知选项，模型一次调用返回各个选项经过校准的概率。它擅长的是**业务标准化**——前提是眼前发生的事，正好落在提前列好的选项清单里；一旦遇到清单之外的情况，它能做的就是老老实实转人工。
2. **通用 Agent（给模型 shell 和文件读写）**：把规则文档、数据表和命令行全部交给模型，让它自己读制度、写脚本、算结果。它足够灵活，但每次都得从头推演业务规则，步骤多、开销高，而且开放 shell 意味着执行边界和审计成本都不好控制。

我们想验证第三条路：**执行标准化**。

不去奢望把未来所有业务例外都提前枚举出来，而是把一项业务拆成一组小而确定的**领域工具（Domain Tool）**——每个工具只负责一个业务步骤，并且严格按人定下的规则执行。模型不需要自己发明公式，只需要根据眼前的新情况，把这些步骤重新组合起来。

在 **DeepSeek Harness（DSH）** 里，一套为特定任务搭配好的固定提示词与有限工具集叫做 **Loadout**；当里面的工具是为某个业务领域专门编写的，就叫做 **Domain Loadout**。由于 DSH 的工具层是开放且可替换的——这是 Codex、Claude Code 这类封闭 harness 没有提供的能力——一个 Domain Loadout 本质上就是一个插件，不需要微调任何模型权重，直接就能配给便宜的小模型运行。

为了看清这条路到底行不行，我们拿三个已脱敏的真实酒店后台案例做了约 **880 次**真实计费测试，把 Domain Loadout、通用 Agent 工具、脚本组、粗粒度流程工具以及 TypeSafe 的 **JEV 1.14** 放在同一套题上逐一对照。

## 先把测试方式讲清楚

我们选取了**三个真实的酒店后台案例（已脱敏）**，涵盖财务、人事与运营三个常见后台环节：

<div class="table-wrap benchmark-table">

| 案例 | 交付物 | 常见非标准事件举例 |
| --- | --- | --- |
| **销售提成** | 月度销售提成表 | 月中离职与交接、联合销售 50/50 拆分、部分退款、归属下月的跨月账单、按人例外的预留比例 |
| **排班考勤** | 月度员工考勤结算 | 离职取消班次（按最小在岗人数规则自动安排顶班并折现余休）、外派培训、按部门区分的节假日政策 |
| **竞品调价监控** | 每周竞品调价预警 | 预订平台（OTA）含早价折算、促销窗口切换阈值、房型页面配反、手工核价的合规校验 |

</div>

为了让结果经得起推敲，整套评测定下了几条硬标准：

- **训练与测试严格隔离**：每个案例 14 道题，共 **42 道题**。其中 6 道作为训练集（1 标准 + 2 中等 + 3 困难），另留出 **8 道测试题**（2 标准 + 3 中等 + 3 困难），使用不同月份或周次的真实业务数据。工具迭代只看训练集，测试集全程不参与调优。
- **确定性对账判分**：每道题的标准答案由一份独立编写的参考实现算出，并与原业务系统的输出逐项核对，做到 **0 差异**。判分时不搞模糊打分，结果表里每一行、每一个字段都必须完全一致（金额容差 1 分钱）。
- **真实的 Agent 会话与安全审计**：所有 Agent 对照组都在真实的 DSH headless 会话与隔离工作区中运行，单次上限 40 步、10 分钟。每次运行结束都会做**输入完整性检查**（确保正式输入文件原封未动）和**防污染审计**（只要触碰评测仓库即判无效，全程 0 次触发）。
- **真实扣费记账**：所有费用来自 OpenRouter 的实际账单——本地代理固定模型供应商并记录每次调用扣费，总额与 API key 账单对账误差在 1% 以内。

在留出测试集的主对照实验里，我们在 `deepseek-v4.1-flash` 上对比了六组方案（每题跑 3 次，每组共 18 次标准题、54 次非标准题）：

这组数据里有三个最值得说清的发现——既有 Domain Loadout 的优势，也有我们不该夸大的边界：

### 1. 标准任务上，JEV 的表现非常出色

如果业务本来就是标准流程，用 Agent 反而大材小用。在 18 次标准测试题里，**JEV 1.14 全部选对（18/18）**，平均每次仅花费约 **$0.00003**、耗时 **0.5 秒**——比 Domain Loadout（$0.0066、14 秒）**便宜约 200 倍、快约 30 倍**。

更难得的是它的概率校准很扎实：在标准题上，它给正确流程的概率落在 **0.64–0.95**，剩下的概率几乎全给了“转人工”，**从未给错误流程分配超过 0.01 的概率**。而在 54 次非标准任务里，它每一次都以接近 **1.00** 的概率返回“转人工”。它极其诚实，也极其精准，但它的能力边界就是选项列表的边界——遇到非标准事件，它能做且只能做“及时停下、交给人处理”。

### 2. 在 `deepseek-v4.1-flash` 上，Domain Loadout 赢的不是正确率，而是省钱、快和可控

必须实话实说：`deepseek-v4.1-flash` 本身很能干。只要给它 bash 和文件读写，**通用工具组（54/54）和脚本组（54/54）同样拿到了 100% 通过率**。

因此，在 flash 上，Domain Loadout 相比通用工具的优势**不是正确率**，而是**成本、速度与治理边界**：
- 同样 100% 做完非标准任务，Domain Loadout **便宜 14%**（$0.0131 vs $0.0153）、**快 36%**（38s vs 59s）、**步数少 23%**（9.3 vs 12.1）；
- 在最复杂的困难题上，差距依然明显：**$0.0179 / 56s** 对比通用工具的 **$0.0204 / 77s**；
- 更重要的是执行边界：全程**没有 shell**，对正式输入文件**只有只读权限**，模型的每一次调用都是语义清晰、有规可查的业务动作。

不过这里也有一个**反例**值得记下来：在竞品调价监控的困难题（`pricing-hard`）上，Domain Loadout 的单次成本反而高于通用工具（**$0.0247** 对比 **$0.0130**）。所以我们不会说 Domain Loadout 在所有细分题型上都一定更便宜。

### 3. 把整个预设流程打包成一个“大工具”，是最差的做法

很多团队给 Agent 接业务系统的第一直觉，是把现有的批处理流程直接包成一个工具丢给模型。实测结果很残酷：**粗粒度流程工具在非标准题上 0/54 全军覆没**，却烧掉了 Domain Loadout **约 6 倍的费用**（$0.0761）和 **7 倍的时间**（257 秒，平均折腾 31.2 步）。工具表达不了业务变化，模型就只能不断重试空转。

更让人警醒的是早期试跑中出现过的一幕：**模型为了逼着这个死板的流程工具吐出想要的结果，居然临时修改了正式规则文件，跑完流程后再把文件改回去。** 正是这次插曲，促使我们给所有评测组都加上了“正式输入不得被篡改”的完整性校验，并把 Domain Loadout 的文件工具彻底锁成只读。

## 结果二：换到更便宜的小模型，差距更明显——以及省的钱到底来自哪

把同样的非标准测试放到另外两款小模型上——每款跑完 24 道留出测试题 × 2 次，只对比**通用工具**与 **Domain Loadout**——你会发现，把业务规则固化进工具的效率红利会随着模型变轻而迅速放大。

### 拆开真实账单：省的钱是 Input token 减少，还是 Output token 减少？

很多人第一反应会猜“是不是工具提示词更短、省了 Input token”。把 OpenRouter 真实账单按未缓存输入、缓存读/写与输出逐项拆开后，答案比直觉更有意思——**省钱来自两股力量叠加：① 步数下降打断了多轮对话的上下文滚雪球（缓存读/写大幅减少）；② 不用从零写脚本、少试错，直接砍掉了高单价的 Output token。** 而且不同模型上谁占主导并不一样：

<div class="table-wrap benchmark-table">

| 模型（非标题均值） | 组别 | 步数 | 总 Input（费用） | Output（费用） | 降本主要来源 |
| --- | --- | --- | --- | --- | --- |
| `deepseek-v4.1-flash` | 通用工具 | 12.1 | 312k（$0.0067） | 14,855（$0.0084） | — |
| `deepseek-v4.1-flash` | **Domain Loadout** | **9.3** | 374k（$0.0080） | **8,973（$0.0051）** | **Input 反增 $0.0013；省钱全靠 Output 暴跌 40%**（省 $0.0033） |
| `gpt-6-luna` | 通用工具 | 10.3 | 253.5k（$0.0064） | 3,754（$0.0019） | — |
| `gpt-6-luna` | **Domain Loadout** | **6.6** | **66.9k（$0.0024）** | **1,086（$0.0005）** | **Input 贡献 75%**（缓存写 44% + 缓存读 31%）+ **Output 贡献 25%** |
| `mimo-v2.6-flash` | 通用工具 | 12.5 | 272.3k（$0.0067） | 12,109（$0.0034） | — |
| `mimo-v2.6-flash` | **Domain Loadout** | **9.6** | **168.8k（$0.0059）** | **8,329（$0.0023）** | **Output 贡献 57%** + **未缓存 Input 28%** + **缓存读 15%** |

</div>

这张明细表同时解释了两个关键现象：
- **为什么 `flash` 的 Input token 反而变多了，但总账单还是更省？** 在提成和调价题里，`flash` 经常把大段工具返回或整份数据读进上下文（这也是 `pricing-hard` 反例更贵的原因），总 Input 反而多了约 62k；但由于 `flash` 的输出单价（$0.567/M）是未缓存输入的 **11 倍**、缓存命中的 **31 倍**，通用工具组每题都要手写并调试脚本、吐出 `14.9k` 输出 token，而 Domain Loadout 只需发出紧凑的结构化工具调用，**把高价 Output 直接砍掉 40%**，轻松覆盖了输入的增加。
- **为什么 `gpt-6-luna` 能一口气省下 65%？** `luna` 不仅步数从 `10.3` 降到 `6.6`，还会老老实实通过 `*_query` 按条件筛数据，单步平均上下文从 `24.5k` 压到 `10.2k`——总 Input 暴降 **74%**（缓存写从 `33.6k` 降到 `14.7k`，缓存读从 `219.9k` 降到 `52.2k`），同时 Output 暴降 **71%**，输入和输出两侧一起省钱。

## 结果三：两轮工具迭代实现泛化——以及这套工具能覆盖多远

| **r1** | 35/36（97%） | $0.0117 | 所有失败都源于“工具表达不了”，于是补充了一批通用领域原语 |
| **r2** | 36/36（100%） | $0.0120 | 最后一处失败是模型手工逐条改价格出错，给快照数据工具补上了批量重标/归一化能力 |

</div>

第 1 轮补进去的，都不是针对某一道题的“特判补丁”，而是五个能跨场景复用的基础原语：

- **`table_merge`**：当例外规则只针对部分员工或销售时，用例外规则另算一张表，再把对应行合并回主表；
- **账单批量筛选与修改**：支持按客人姓名、日期范围与支付方式筛选账单并批量处理；
- **`ledger_split`**：支持联合销售按比例拆分账单；
- **`roster_cancel_shifts`**：取消离职人员班次，并自动按最小在岗人数规则安排顶班；
- **余休折现**：在考勤结算工具里支持调休余额折现。

在**全程未参与调优的留出测试集**上，这两轮工具修改带来了立竿见影的跃升：
- 非标准题通过率从 v0 的 **42/54（78%）**跃升到 **54/54（100%）**；
- 困难题从 **15/27（56%）**升到 **27/27（100%）**，平均耗时从 **150 秒**降到 **56 秒**，平均成本从 **$0.0477** 降到 **$0.0179**（共省 $0.0298，降幅 **62%**）。拆开这两轮改工具省下的钱：**59% 来自缓存读大降**（步数从 23.3 步压到 10.5 步，缓存读从 `1,392k` 降到 `421k`，少重读了十几轮历史上下文），**41% 来自 Output 暴跌 60%**（`35,832 → 14,388`，不再手工逐条改价或空转试错），未缓存输入几乎不变（约占 0.5%）。

整个研究跑完约 **880 次**正式判分运行，连同调试和冒烟测试在内，所有模型调用的总花费加起来也就 **约 $14**。

### 泛用性到底如何？换题目、换业务场景能覆盖多远？

看清工具的真实结构，就能准确判断它的覆盖范围，不神化也不低估。三个案例虽然业务不同，但底层 6–8 个工具都按同一套**四段式原语**搭成：**查/改规则副本（`*_rules_view` / `*_rules_derive`）→ 查/批量改数据副本（`*_query` / `*_derive` + 少量业务动作）→ 确定性结算引擎（`*_compute`）→ 跨表行级合并（`table_merge`）**。

把它放到真实业务变化里，能覆盖和不能覆盖的边界很清晰：

- **不用改工具就能直接 cover 的变化**：
  - **换时间周期与明细数据**：换月份、换周次、换人名/房型/平台名称与具体金额比例（留出测试集本身就是全新月份与周次的数据）。
  - **已有例外机制的任意组合叠加**：比如把“月中离职交接 + 联合销售任意比例拆分 + 跨月账单剔除 + 个别员工例外预留比例 + 手工扣款”自由叠在一起，模型只需重新编排原语调用顺序就能解出（留出测试的 27/27 困难题正是各类叠加）。
  - **参数级临时政策调整**：促销窗口临时改涨跌阈值、某部门单独切节假日加班费/调休政策、停用某监控平台或改缓存天数，都可以靠规则副本派生 + `table_merge` 直接接住。
- **当前工具 cover 不了的真实边界**：
  - **同一业务内冒出“现有原语语义表达不了”的新机制（跨大类例外）**：例如提成规则突然新增“按当月全店入住率动态加权”，或排班引入“外包小时工按小时计薪”——由于结算引擎和工具 schema 里没有对应概念，模型又没有 shell，它**无法凭空硬算**。此时的维护方式不是去训模型，而是像 `r0 → r1 → r2` 那样，由业务专家或工程师把缺的那一步补成新原语或新参数，补完即可覆盖今后同类的新组合。
  - **换到完全不同的行业或业务线（如电商售后、供应链对账、保险理赔）**：这套针对酒店后台写的具体工具包**不能直接拿过去用**——每个行业的数据表结构与结算规则不同，需要为新业务写它自己的 6–8 个 Domain Tool。**真正跨行业通用的是这套 Loadout 范式本身**：只要业务满足“有正式主规则 + 结构化台账 + 频繁非标准例外 + 强审计要求”（财务核算、薪酬提成、排班考勤、运营监控、对账复核都属于这一类），就可以套用同样的四段式原语和 1–2 轮失败驱动迭代来落地。

## 为什么选 Domain Loadout，而不是微调模型或给通用 Agent 挂 MCP？

把这组实测放到更常见的工程路线里对照，就能看出**直接替换并迭代工具 schema 的 Domain Loadout**，与**微调模型（Fine-tune）**和**MCP 外挂**的本质区别：

<div class="table-wrap benchmark-table">

| 工程路线 | 改的是什么 | 维护与迭代成本 | 执行边界与上下文控制 |
| --- | --- | --- | --- |
| **微调模型（Fine-tune）** | **模型权重**（把规则隐式压进参数） | 需要攒标注样本、跑训练、管模型版本；业务规则一变就过期，得重训 | 权重本身提供不了硬性权限护栏，算错或越权依然难以事前拦截与审计 |
| **MCP 外挂** | 在封闭 harness 既有工具**之上叠加**外部工具 | 接入方便，但如果把大流程直接包成一个粗粒度 tool，非标场景会 0/54 空转 | Codex / Claude Code 等封闭宿主自带的 shell 与文件写权限通常拿不掉；MCP 接多了 tool schema 膨胀占上下文，模型仍可能绕过业务工具直接改底层文件 |
| **DSH 的 Domain Loadout** | **直接替换并收口**底层工具集，迭代细粒度工具 schema | **不碰权重**；只看失败样本补 1–2 轮通用原语（本次总花费约 $14），规则写在代码里随时可改 | 依托 DSH 开放可替换的工具层，直接撤掉 shell、锁死正式输入只读，每个任务只暴露 6–8 个精准工具，上下文干净且每步操作可审计 |

</div>

关键区别就在“**叠加**”和“**替换收口**”这四个字上。

在封闭 harness 里挂 MCP，本质上是在通用 Agent 的满桌工具旁边再多摆几把工具——如果底层 shell 还在，模型一遇到卡壳就可能绕路去改文件（就像我们早期试跑里粗粒度组偷偷改规则文件再改回去的那一幕）；如果把一堆业务接口一股脑挂进 MCP，膨胀的 tool schema 还会持续消耗上下文并干扰小模型决策。而在 DSH 里做 Domain Loadout，是把工具层本身当成可替换的插件：拿掉不需要的通用权限，只留下经过打磨、语义对齐业务的 6–8 个工具 schema，让便宜的小模型把注意力全部放在“组合步骤”上。

## 回到业务落地：两种标准化不是替代，而是互补

把这三组实验拼在一起，企业后台自动化的分工其实非常清晰：

1. **标准业务交给决策模型（业务标准化）**：像 JEV 1.14 这样的决策式系统，在已知标准路径上既准又快，成本低出两个数量级，而且不知道的时候会干脆地升级转出。把能标准化的高频流程交给它，是最划算的第一道防线。
2. **非标准业务交给“小模型 + Domain Loadout”（执行标准化）**：那些占了 80% 以上一线时间的例外情况，不需要微调模型，也千万别把僵硬流程包成一个粗粒度大工具。把业务拆成细粒度的 Domain Tool、拿掉 shell、锁住正式输入只读，便宜小模型就能用更低成本、更快速度、在清晰可审计的护栏内把活干完。
3. **开放的工具层是前提**：能够按任务直接替换底层工具集、把一组业务原语打包成插件按需装卸，依赖于 **DeepSeek Harness（DSH）** 开放、可替换的工具层架构。想进一步了解基于 DSH 的 Bot 与工作区配置，可以从[产品概览](/docs/overview/)和[安装指南](/docs/installation/)开始。

## 本次评测的局限与说明

为了方便读者准确评估这些数字的适用范围，我们把本次实验的边界全部摊开说明：

- **样本规模有限**：共 3 个酒店后台案例、42 道任务、每题重复 2–3 次，结论尚不能直接外推到所有行业与任务形态。
- **同类别泛化**：留出测试集里的业务事件虽然换了月份、周次和具体细节，但与训练集属于同一类业务例外（离职、拆分、按人例外等）；本次没有测试跨大类的零样本泛化。
- **JEV 的测试设定**：JEV 1.14 仅在单一形态下测试——即单次 `choice` 决策，输入为业务请求文本，不传入文件内容。作为对照，我们也用 `deepseek-v4.1-flash` 模拟了同样的选项路由器，得到了完全一致的通过率（标准题 18/18、非标准题 0/54），但单次成本约为 JEV 的 7 倍。
- **工具装配方式**：通用工具组采用 DSH 标准工具集；在 headless 模式下，各 Loadout 通过 profile 叠加层装配（效果等价于一个 preset：每个会话固定提示词与受限工具集）。
- **判分器修正与统一重判**：在查看测试结果后，我们发现判分器的浮点数比较会把“恰好相差 1 分钱”误判为失败，违背了事先声明的 1 分钱容差。修正该缺陷后，我们用同一套规则重新判分了全部已保存的运行结果，共有 **9 次**运行从失败翻转为通过。本文呈现的所有数字均为修正重判后的最终结果。
