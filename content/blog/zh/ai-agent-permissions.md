把一个 AI Bot 拉进公司群聊后，每位成员都能 @ 它。它既可以通过命令行读取团队邮箱，也能修改代码库。问题随之而来：**同事 A 负责跟进项目邮件，同事 B 只参与代码讨论。如果两人发出同样的查邮件请求，Bot 怎么知道该帮谁查、该拒绝谁？**

在多人共享的群聊里，AI Agent 的权限管理至少要回答四个问题：

1. **谁能发起请求？** 识别消息背后的真实请求者，并判断对方是否获准与 Bot 对话。
2. **Bot 该怎样对待这个人的请求？** 根据用户的角色策略来决定哪些事能做、哪些事要拒绝。
3. **谁能批准敏感操作？** 检查点击审批按钮的人是否具备相应的管理权限。
4. **底层进程能接触什么资源？** 看执行环境手握哪些凭据、边界设在哪里。

我们的设计思路是把这四件事拆开处理：**用确定性的程序把守请求入口，让 Bot 在需要时主动查询请求者的角色、按自然语言编写的策略行事，再分别管好管理审批与底层执行凭据。**

本文基于 DeepSeekBot 的[角色与准入设计提案](https://github.com/BotHarness/DeepSeekBot/issues/1371)，下面我们用一个“团队邮件助手”的场景，聊聊这套方案背后的设计取舍。

## 业界先例：自然语言策略到底控制了什么？

“用自然语言写权限规则”在业内已有不少探索，但不同方案把控制点放在了不同位置：

| 路线 | 文字规则用于什么 | 实际控制位置 |
| --- | --- | --- |
| 主 Agent 行为策略 | 模型读取规则，决定如何回应请求 | 模型生成行为；纯文字本身不负责底层拦截 |
| Hermes smart policy | 辅助模型判断高风险命令应批准、拒绝还是转交人工 | 命令审批流程；主要针对命令风险而非群成员角色 |
| AWS AgentCore | 将自然语言要求转换成结构化的 Cedar 策略 | Gateway 在工具调用前执行确定性策略判定 |

比如 Hermes 的 `approvals.smart_policy`（[源码](https://github.com/NousResearch/hermes-agent/blob/66605471e9f0b0832abbefaf625ce08e948ca540/tools/approval_smart.py)）让管理员用自然语言写规则，由独立的 guardian 模型评估被标记的命令。它解决的是**单条命令的风险评估**，而不是多人共享群聊里的角色区分。Hermes 社区里也有过一个很有代表性的[讨论（#3897）](https://github.com/NousResearch/hermes-agent/issues/3897)：有团队把“非管理员不能执行终端命令”写进主模型 prompt，结果模型还是执行了命令，促使他们进一步寻求按用户限制工具的机制。

AWS AgentCore 则采用了另一条路线（[博客介绍](https://aws.amazon.com/blogs/machine-learning/secure-ai-agents-with-policy-in-amazon-bedrock-agentcore/)）：用自然语言生成并校验 Cedar 策略，运行时由 Gateway 在工具调用前做确定性拦截。自然语言只是编写入口，真正执行的是结构化策略。

DeepSeekBot 的提案选择了更贴合个人与小团队宿主环境的组合：用代码严格把控谁能触发 Bot、谁能点审批；而在具体的业务交互上，给 Bot 提供按需查询角色的工具，用自然语言灵活表达业务规则。

## 核心设计：四道边界各司其职

把这四道边界画出来，每一层负责的事情就很清楚了：

```text
群消息
  ↓ 程序准入
带可信作者的请求
  ↓ Bot 按需查询当前角色
模型按角色策略处理请求

管理动作
  → Host 检查管理能力
Shell 资源访问
  → 凭据和执行环境决定
```

### 1. 程序准入与可信身份

请求者的身份必须来自聊天平台认证的真实发送者 ID，绝不能靠群昵称、自称“我是管理员”或者引用一段别人的聊天记录来推断。同时，身份天然带有当前 Bot 和应用绑定的作用域——Slack 上的同名用户不会自动等同于飞书用户，在 Bot A 那里获准配对，也不代表能直接指挥 Bot B。

假设邮件助手所在的群是受限群。当尚未配对的同事 A 第一次 @ Bot 时，程序会直接拦截并回复固定的配对申请提示。**这一步完全不调用大模型，也不会把被拦住的请求塞进待执行队列。**

等管理员审核通过并为 A 分配角色后，系统会通知 A 重新提问，而不是自动重放几个小时前的旧请求——否则一条早就过时的指令可能会在审核通过的瞬间突然执行。反过来，一旦撤销配对，下一次请求依然会在进入模型之前被直接拦下。

### 2. 按需查询角色，既省上下文又不怕配置过期

如果把整个团队的角色名单长期塞进 system prompt，不仅浪费上下文，群成员较多时也容易干扰模型注意力；而如果在每条消息里直接硬编码当时的权限快照，一旦管理员中途改了角色，历史消息里的旧权限就很容易造成混淆。

因此，我们选择在每条消息上保留可信的作者标识，再给 Bot 提供一个只读的单人权限查询工具。平时普通寒暄不必查角色；当遇到受角色约束的业务请求时，Bot 会根据当前请求者的真实身份去查最新配置，而不会从上下文里借用别人的权限。

比如当 A 问“今天有哪些邮件需要跟进”时，Bot 查到的结果长这样：

```text
配对状态：已批准
角色：邮件查询员
行为策略：允许查询和整理；不允许编辑或发送
管理能力：空
策略版本：7
查询时间：2026-10-11T09:00:00Z
```

当管理员修改了 A 的角色后，下一次查询就会返回新的策略版本号，而对话历史里的“版本 7”只作为当时的查询记录留存。

当然，**查询工具的作用是提供最新信息，它本身并不替代底层拦截。** 行为指引会要求模型在身份无法解析或查询失败时暂缓操作，但这依然属于模型层面的配合，不能等同于操作系统级别的强制隔离。

### 3. 自然语言策略与结构化管理能力分开

管理员可以给 A 分配这样的角色：

```text
角色：邮件查询员

行为策略：
允许查询公司邮箱并整理待跟进事项。
不允许编辑草稿或发送邮件。

结构化管理能力：空
```

为什么分成两部分？因为业务规则往往千差万别，比如“可以汇总项目邮件，但不要透露薪资数字”，用自然语言写最自然，模型在处理请求时也最容易理解。

而像“能不能批准一次高风险工具调用”这样的管理动作，则必须用结构化能力来定义，由运行 Bot 的 Host 进程直接校验操作者身份。没有相应管理能力的人，哪怕在界面上看到了审批卡片，或者在群里自称管理员，Host 也会直接拒绝他的审批操作。简单来说：**模型负责遵守自然语言业务策略，程序负责校验结构化管理权限。**

### 4. 认清底线：自然语言规则管不住进程已有的凭据

在我们的邮件助手场景里，Bot 是通过 Shell 调用 Himalaya CLI 来读邮件的。这就引出了最关键的一条底线：**如果运行 Bot 的底层进程本身就握有邮箱凭据，那么在 B 的角色里写一句“禁止查询邮件”，并不能让操作系统在底层拒绝读取邮箱。**

同样地，如果只限制某个专门的邮件 Tool，却放开了能访问同一份凭据的 Bash，也防不住绕过。当你确实需要严格的资源隔离时，正确的做法是缩小 Bot 进程的凭据范围、为不同权限的团队拆分成独立的 Bot 实例或沙箱环境，或者在执行路径上加上确定性的网关校验（可参考 [AWS AgentCore 策略说明](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-natural-language.html)与 [pi-chat 执行环境](https://github.com/earendil-works/pi-chat/blob/9adbd29b40ee27ff1decf0fc87cbe180b40924f5/src/gondolin.ts)）。

把自然语言策略的灵活性和底层凭据的物理边界坦诚地分开，反而能让团队在部署时做出更安全的决定。

## 同群多人：谁提问、谁是背景、谁能看到回复？

群聊里还有一个常见情况：同事 B 没有查邮件的权限，但他刚才在群里聊了几句项目背景；随后同事 A @ Bot 要求查相关邮件。

这时候，收集群消息和触发任务是分开处理的（类似 Pi 生态中 [`pi-chat` 的做法](https://github.com/earendil-works/pi-chat/blob/9adbd29b40ee27ff1decf0fc87cbe180b40924f5/src/runtime.ts)）。B 的发言可以作为群聊上下文保留下来，但 B 不会因为出现在上下文里就自动获得 A 的权限；反过来，别人引用了一句管理员的话，也不会让自己变成当前请求者。

另外别忘了群聊的可见性：**A 有权提问，并不代表 Bot 发在群里的回复只有 A 能看见。** 既然是在公共群里回复，群里的其他成员自然也能读到。因此涉及敏感内容的邮件查询，还是应该放在私聊或受信任的小群里进行。

## 用五个场景检验这套设计

把这套机制落到实际的邮件助手里，可以通过五个具体场景来检验：

1. **陌生成员 @ Bot**：直接收到固定的配对申请提示，不触发大模型调用。
2. **管理员批准 A**：A 收到可以重新提问的通知，先前的旧请求不会自动重放。
3. **A 重新发起邮件查询**：Bot 根据 A 的可信身份查询角色，并按“只查不发”的策略整理邮件。
4. **管理员修改角色策略**：下一次查询立即返回新版本策略，历史记录保留当时的版本号与时间戳。
5. **无管理权限的 B 尝试点审批**：Host 进程直接拒绝该操作；若撤销某人配对，其后续请求会再次在入口处被拦下。

## 常见问题

**这是完整的 RBAC 吗？** 借用了 RBAC“用户 → 角色 → 权限”的组织方式，但其中的业务行为策略由自然语言表达、靠模型理解执行，因此不等同于对所有工具和底层资源做强制拦截的传统 RBAC。

**为什么不在每条消息里直接注入全量权限表？** 按需查询能大幅减少重复上下文，也能确保每次面对受控请求时读到的都是最新配置。

**只读的角色查询 Tool 会赋予用户权限吗？** 不会。它只负责告诉模型“当前这个人是什么角色”；修改角色和批准敏感操作都必须由有权限的管理员通过 Host 程序完成。

**现在能用上这套方案吗？** 本文介绍的是设计提案，具体实现与验收进展可以在[交付跟踪 Issue #1372](https://github.com/BotHarness/DeepSeekBot/issues/1372) 中查看。想了解目前已发布的能力，请参阅[平台与工具范围](/docs/capabilities/)和[外部身份指南](/docs/channel-sidebar/external-identities/)。
