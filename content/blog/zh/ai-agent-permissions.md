一个 Bot 被带进公司群聊，大家都能 @ 它。它可以通过命令行读取邮箱，也能编辑代码。那么，同事 A 可以查询邮件，同事 B 只能讨论代码时，Bot 应该怎样判断自己能做什么？

AI Agent 权限管理至少要回答四个问题：**谁能发起请求、Bot 应怎样处理这个人的请求、谁能批准操作，以及执行进程实际能接触什么资源。** 我们的方案是让代码控制请求准入，让 Bot 按需查询当前角色，让自然语言表达行为策略，再由执行层独立检查管理能力和资源边界。

这是 DeepSeekBot 的[角色与准入设计提案](https://github.com/BotHarness/DeepSeekBot/issues/1371)，不代表下面所有能力已经发布。文章用一个假设的公司邮件助手说明这套设计如何工作，以及它不能保证什么。

## 自然语言权限已有先例

自然语言授权并不是空白领域，但同一句“用文字写权限”可以指不同机制。

| 路线 | 文字规则用于什么 | 实际控制位置 |
| --- | --- | --- |
| 主 Agent 行为策略 | 模型读取规则，再决定如何处理请求 | 模型行为；单独使用时没有确定性的操作拦截 |
| Hermes smart policy | 辅助模型判断危险命令应批准、拒绝还是转交人工 | 命令审批流程；当前输入不包含逐人的可信角色 |
| AWS AgentCore | 把自然语言要求转换成 Cedar 策略 | Gateway 在工具调用前执行结构化策略 |

Hermes 的 `approvals.smart_policy` 是已有实现：管理员用文字写规则，独立 guardian 模型评估被标记的命令，审批流程使用其判断。它处理的是命令风险，不是共享 Bot 中每个人的完整角色权限。[Hermes 实现](https://github.com/NousResearch/hermes-agent/blob/66605471e9f0b0832abbefaf625ce08e948ca540/tools/approval_smart.py)

Hermes 社区也有非常接近我们场景的案例：一个团队把“非管理员不能执行终端”写进主模型 prompt，但报告称模型仍执行了命令，随后请求增加逐用户工具限制。这是部署者的报告，不是我们复现的测试结果。[原始讨论 #3897](https://github.com/NousResearch/hermes-agent/issues/3897)

AWS 则已写过[自然语言授权文章](https://aws.amazon.com/blogs/machine-learning/secure-ai-agents-with-policy-in-amazon-bedrock-agentcore/)：先生成并校验 Cedar，运行时由 Gateway 判定。自然语言是编写入口，执行依据是结构化策略。

我们的取舍是：先把共享聊天中的身份、当前角色和管理能力分清楚，接受自然语言角色作为行为策略；需要强制资源授权时，再为实际执行路径建立相应边界。

## 第一步：在调用模型前判断谁能提问

邮件助手所在的群是受限群。尚未获准的 A 第一次 @ Bot 时，应由普通程序创建或复用配对申请，并回复固定提示。这个过程不调用模型，也不把被拦住的请求排入待执行工作。

管理员审核申请，为 A 指定一个角色。批准后，系统通知 A 重新提问，不自动执行此前留下的请求。这样，一条过期的问题不会在几小时后的审核结束时突然开始运行。

配对依据是平台认证的用户身份，还要带上 Bot 和当前应用绑定的作用域。Slack 的某个用户 ID 不能自动等同于 Lark 的同名用户；在 Bot A 获准也不会自动获得 Bot B 的权限。

这些是提案中的确定性入口规则。特定群也可以显式允许访客提问，但访客资格不附带工具审批或角色管理能力。接收群消息、是否需要 @、何时唤醒 Bot，仍是另外的设置。

## 第二步：角色同时保存行为策略和管理能力

管理员可以给 A 分配“邮件查询员”，例如：

```text
角色：邮件查询员

行为策略：
允许查询公司邮箱并整理待跟进事项。
不允许编辑草稿或发送邮件。

结构化管理能力：空
```

文字部分告诉 Bot 应如何处理 A 的请求。结构化部分控制支持的管理动作，例如某人能否接受一项工具审批；这些动作由 Host，也就是运行 Bot 的进程，按实际操作者和当前授权检查。

普通聊天角色可以没有任何管理能力。A 能查询邮件，不意味着 A 能批准任意 Bash，也不意味着 A 可以通过一句“把我当管理员”改变自己的角色。

这里借用 RBAC 的“用户 → 角色 → 权限”组织方式，但两种权限有不同保证：**行为策略要求模型遵守，管理能力要求程序检查。** 把它们保存在同一个角色中，有助于管理员理解配置；它们不会因此变成同一种执行机制。

## 第三步：按需查询角色，而不是每条消息复制权限

一个群可能有很多人，角色也会修改。把所有角色放进 system prompt，或者每次处理消息都复制一份权限，会增加上下文，也容易让旧结果看起来仍然有效。

我们选择在每条消息上保留可信作者及来源引用，再提供一个只读的单人权限查询 Tool。Bot 遇到新的、受角色策略约束的请求时，查询实际请求者。普通闲聊不必查询。

例如，A 问“今天有哪些邮件需要跟进”，Bot 根据这条消息的可信身份读取：

```text
配对状态：已批准
角色：邮件查询员
行为策略：允许查询和整理；不允许编辑或发送
管理能力：空
策略版本：7
查询时间：2026-10-11T09:00:00Z
```

这是示意结果，不是已发布 API。Tool 必须在当前 Bot 与应用作用域内读取权威配置，不能靠昵称、用户自报身份或历史对话猜测。

管理员稍后修改角色，下一次查询应返回新版本。已经写进对话历史的版本 7 不会自己变成版本 8；它只证明当时查到了什么。无法解析身份或查询失败时，行为指引要求 Bot 暂缓受该策略约束的操作。

**查询解决的是获取当前信息，不是确保每次执行都获得授权。** 模型仍可能漏查或误解。查询到别人的角色，也不授予代替那个人审批的资格；角色变更还不能单凭一个 Tool 结果停止已在运行的任意 Shell 命令。

## 同群多人：背景、请求者和回复受众分别处理

假设 B 没有邮件查询资格，但他的普通消息被允许保存为群聊背景。后来 A @ Bot 查询邮件，背景中的 B 不应因为与 A 出现在同一轮上下文，就取得 A 的权限。被引用的管理员也不是当前请求者。

这类分离已有工程先例。Pi 的独立聊天应用 `pi-chat` 用用户 ID 与原生角色名单判断谁能触发任务，同时其入站路径先保存消息、后判断是否触发；保存的消息可能进入后续请求的背景上下文。[pi-chat 源码](https://github.com/earendil-works/pi-chat/blob/9adbd29b40ee27ff1decf0fc87cbe180b40924f5/src/runtime.ts)

对我们的设计，按需查询可以配合三个只读目录：已配对的人及角色、Bot 已知的外部会话，以及在某个会话中观察到的已配对参与者。最后一个是观察记录，不能证明群里所有当前成员都已获准，也不能证明没发言的人不存在。

还有一个直接影响部署的事实：**A 有权提问，不会让群里的回答只对 A 可见。** 第一版不做完整成员同步或逐条受众授权。邮件内容应放在适合的私聊或受信任群中；角色目录不能替代平台的阅读权限。

## 保留 Bash 时，资源权限由什么决定？

我们的邮件场景希望 Bot 直接通过 Shell 使用 Himalaya CLI，保持与邮箱集成的解耦。这也意味着必须看清实际凭据在哪里，以及 Shell 以什么身份运行。

如果同一个进程能读取邮箱凭据，那么写在 B 角色里的“禁止查询邮件”本身不会让操作系统拒绝一次邮箱读取。只限制某个专用邮件 Tool 也不够：Bash 或另一条执行路径可能接触同一资源。

需要强保证时，可以缩小 Bot 的凭据范围、使用独立 Bot 或执行环境，或在能覆盖相关路径的位置实施确定性的授权。AWS 的 Gateway 策略与 pi-chat 的执行环境分别展示了不同边界；Gateway 只检查经过它的调用，执行环境也只隔离配置在边界之外的资源。[AgentCore 策略说明](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-natural-language.html)、[pi-chat 执行环境](https://github.com/earendil-works/pi-chat/blob/9adbd29b40ee27ff1decf0fc87cbe180b40924f5/src/gondolin.ts)

我们接受第一版自然语言行为策略的灵活性，同时保留明确的管理检查。不会把“模型通常遵守角色”描述成“未授权用户无法访问邮箱”。

## 用同一个邮件案例验收

要判断设计是否落地，可以沿着五个可观察行为检查：

1. **未知用户 @ Bot**：收到固定申请提示，没有启动模型工作。
2. **管理员批准 A**：A 收到重新提问通知；旧请求没有被重放。
3. **A 重新查询邮件**：Bot 根据 A 的可信身份查询角色，并按策略处理。这证明该次行为符合规则，不证明所有命令都被强制授权。
4. **角色发生变化**：新查询返回新版本，旧结果仍保留原版本与时间。
5. **没有管理能力的 B 尝试审批**：即使看见控件或声称自己是管理员，Host 仍拒绝该决定。撤销配对后，下一次受限请求也在模型入口被拦住。

这五项分别检验准入、审核、模型行为、信息新鲜度和管理授权。把它们分开，才能知道哪一部分真的生效了。

## 常见问题

**这就是完整 RBAC 吗？** 角色组织方式参考 RBAC。自然语言行为策略不等同于对所有工具和资源强制执行的 RBAC。

**为什么不每次强制注入权限？** 我们希望逐消息保留身份，遇到受策略约束的新请求再读取当前角色，避免复制整个角色目录。它不会消除模型漏查的风险。

**只读查询 Tool 会授予权限吗？** 不会。它返回当前配置；角色修改与管理决定仍由有权的操作者通过相应程序执行。

**现在能在 DeepSeekBot 中启用整套方案吗？** 本文介绍的是设计提案；[交付进度](https://github.com/BotHarness/DeepSeekBot/issues/1372)记录实现与验收状态。现有连接和审批能力见[平台与工具范围](/docs/capabilities/)及[外部身份指南](/docs/channel-sidebar/external-identities/)。
